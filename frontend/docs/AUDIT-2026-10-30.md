# Audit Teknis RODE — 30 Oktober 2026

## Tujuan dan ruang lingkup

Laporan ini membantu maintainer memprioritaskan perbaikan dan menyiapkan verifikasi sebelum aplikasi dipakai lebih luas. Audit membaca source aplikasi, route API, service bisnis, konfigurasi, dokumentasi, dan tes yang tersedia. Audit bersifat read-only; tidak ada perubahan kode.

Pemeriksaan runtime belum dilakukan. Clone ini tidak memiliki `node_modules` atau file `.env`. Instalasi Yarn dengan lockfile terkunci tertahan pada tahap fetch paket (termasuk saat paket opsional diabaikan), lalu dihentikan. Karena itu server, tes, typecheck, dan build belum dijalankan. Temuan di bawah adalah hasil inspeksi source, bukan klaim bahwa perilaku runtime sudah direproduksi.

## Ringkasan

Arsitektur aplikasi relatif terpisah dengan jelas: Next.js menjadi aplikasi dan API utama, service menangani aturan bisnis, Drizzle mengakses PostgreSQL/PGlite, sedangkan backend Python menjadi proxy preview. Pemeriksaan role, ownership transaksi, validasi input umum, idempotensi, optimistic locking, dan audit koreksi telah tampak di kode.

> Ada empat tindak lanjut yang disarankan sebelum go-live: lindungi token Smart TV dari URL, perketat validasi jam dan tanggal, serta satukan perubahan master dengan audit log dalam satu transaksi database.

## Temuan

### AUD-01 — Sedang: token Smart TV berada di URL

**Lokasi:** `src/app/display/production/page.tsx` (pembacaan token dari query), `src/components/display/DisplayBoard.tsx` (token diteruskan pada query API), `src/app/api/display/route.ts` (token diterima dari header atau query).

**Dampak:** token tampil pada URL halaman dan request API. URL dapat tersimpan di riwayat browser dan log proxy/server. Kebijakan referrer saat ini `strict-origin-when-cross-origin` tetap mengirim URL penuh pada request same-origin, sehingga nilai query dapat ikut terekspos sebagai referrer. Pemegang token dapat membaca ringkasan produksi sampai token dicabut.

**Perbaikan:** gunakan fragment URL untuk bootstrap token (fragment tidak dikirim ke server), pindahkan token ke header request setelah dibaca, lalu hapus token dari address bar dengan `history.replaceState`. Tetapkan `Referrer-Policy: no-referrer` pada halaman Smart TV, dan pastikan respons API tetap `Cache-Control: no-store`.

### AUD-02 — Sedang: jam `24:xx` diterima oleh parser jadwal

**Lokasi:** `src/lib/time.ts`, fungsi `parseHM`; skema jadwal di `src/services/schedule.ts`.

**Dampak:** parser hanya menolak jam yang lebih besar dari 24, jadi `24:30` lolos. Admin yang menyimpan jadwal dengan jam tersebut dapat menggeser rentang kerja melewati tengah malam secara tidak sengaja. Pencatatan selanjutnya dapat mendapat tanggal kerja atau nomor blok yang keliru.

**Perbaikan:** validasi jam `00–23` dan menit `00–59`. Jika `24:00` dibutuhkan untuk menandai akhir hari, dukung sebagai satu pengecualian eksplisit dan jangan menerima `24:01–24:59`.

### AUD-03 — Rendah–sedang: tanggal kalender tidak divalidasi

**Lokasi:** skema tanggal di `src/services/aggregate.ts` dan `src/services/transactions.ts`; parameter tanggal pada `src/app/api/operator/summary/route.ts`.

**Dampak:** validasi hanya memeriksa bentuk `YYYY-MM-DD`, sehingga nilai seperti `2026-02-31` bisa lolos Zod. Di jalur query atau insert, tanggal seperti ini berpotensi menjadi error database 500 atau menghasilkan perhitungan rentang yang tidak valid.

**Perbaikan:** buat satu validator tanggal yang memastikan tanggal ISO tersebut benar-benar ada di kalender, lalu gunakan di filter, input transaksi, target, jadwal, dan endpoint ringkasan.

### AUD-04 — Sedang: pencatatan audit master terpisah dari mutasi

**Lokasi:** `src/services/master.ts`, fungsi `createEntity` dan `updateEntity`.

**Dampak:** row master ditulis (dan pada alur update, sesi pengguna dapat dihapus) sebelum audit log ditulis. Jika insert audit gagal, API dapat merespons 500 meskipun perubahan sudah tersimpan. Perubahan juga kehilangan jejak audit, yang menyulitkan penelusuran dan dapat membuat admin mengulang operasi.

**Perbaikan:** jalankan mutasi master dan insert audit di satu transaksi database. Jika salah satunya gagal, batalkan keduanya.

## Cakupan yang diperiksa dan belum diperiksa

**Diperiksa:** struktur route dan service aplikasi, autentikasi dan otorisasi, operasi transaksi, agregasi, aturan waktu, konfigurasi admin, display, ekspor, schema database, skrip migrasi/seed, konfigurasi Next.js/Vercel, serta tes Vitest yang ada.

**Belum diverifikasi:** server berjalan, migrasi terhadap database, tes Vitest/Pytest, typecheck, lint, build produksi, browser flows, beban/performa, deployment, dan konfigurasi atau kredensial lingkungan produksi.

## Urutan tindak lanjut

1. Perbaiki AUD-01 dan AUD-02 sebelum link Smart TV dan jadwal dipakai operasional.
2. Jadikan perubahan master dan audit log satu transaksi (AUD-04).
3. Gunakan validator tanggal kalender bersama (AUD-03).
4. Setelah dependensi tersedia, gunakan PGlite lokal untuk menjalankan tes, typecheck, build, lalu smoke test login, input operator, dashboard manajer, admin, laporan, dan Smart TV.
5. Tinjau kembali rate limit in-memory dan dependensi backend sebelum mengandalkan deployment multi-instance.
